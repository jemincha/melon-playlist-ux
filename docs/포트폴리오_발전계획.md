## 1. 프로젝트의 출발점

약 10년간 멜론을 이용하다 다른 플랫폼으로 옮겼다. 내 사용 방식에서는 멤버십 혜택의 활용도가 낮았고, 영상과 음악을 함께 이용할 수 있는 구독 상품의 가치가 더 크게 느껴졌다. 다양한 토크 콘텐츠를 백그라운드로 듣는 경험도 플랫폼 선택에 영향을 주었다. 인기 차트 중심의 음악 탐색은 내 취향의 음악을 찾는 데 충분하지 않았다.

그렇다고 이 프로젝트에서 가격, 콘텐츠 생태계, 브랜드 전략을 모두 해결하려는 것은 아니다. 이탈 경험을 돌아보는 과정에서, 직접 반복해서 겪었고 사용자 과제로 재현할 수 있는 플레이리스트 관리에 집중했다.

좋아하는 곡 수백 개를 카테고리별로 담고, 같은 밴드의 곡을 모아 원하는 흐름으로 듣는 사용 방식에서는 새 곡을 추가하거나 여러 곡을 옮길 때 편집 부담이 생겼다. 원래 제안은 아티스트 기준 정렬과 블록 단위 이동이었다. 기존 MVP는 여기에 신곡을 기존 블록으로 이동하는 방식을 구현했다. 다음 단계에서는 이 세 과제 중 무엇이 중요한지부터 확인한다.

**프로젝트 제목 후보:** 224곡의 플레이리스트, 내가 만든 순서를 유지하며 관리하기

**핵심 질문:** 직접 플레이리스트 순서를 관리하는 사용자가, 기존 감상 흐름을 보존하면서 곡을 모으고 이동하고 추가하는 부담을 줄일 수 있을까?

## 3. 대상 사용자와 문제 정의

### 대상 사용자 가설

음악 스트리밍 앱에서 직접 플레이리스트를 만들고, 곡의 순서를 관리하며, 새 곡을 반복해서 추가하는 사용자. 특히 수백 곡 규모의 목록을 관리하는 사례를 우선 탐색한다. 서비스는 멜론에 한정하지 않고 실제 사용 방식을 비교한다.

연령과 장르는 선정 기준으로 고정하지 않는다. 라이트 리스너, 모든 멜론 사용자, 모든 젊은 사용자의 문제라고 설명하지 않는다.

### 문제 진술

내 경험에서는 원하는 곡을 추가한 뒤 기존 곡이 있는 위치를 찾고 순서를 바꾸는 작업이 반복됐다. 목록이 길어질수록 이 관리 작업이 부담스러웠다. 다른 사용자도 같은 문제를 겪는지, 아티스트 기준이 유효한지, 실제로 어떤 작업이 부담인지 아직 확인하지 않았다.

### 사용자 과제와 해결 후보

| ID | 사용자 과제 | 해결 후보 | 검증할 점 |
|---|---|---|---|
| J1 | 흩어진 곡을 아티스트별로 찾아보고 모으고 싶다. | 아티스트 기준 정렬·그룹화 | 보기 순서만 바꾸려는가, 실제 감상 순서도 바꾸려는가? |
| J2 | 여러 곡을 묶어 원하는 위치로 옮기고 싶다. | 블록 단위 이동 | 아티스트가 묶음 기준인가, 앨범·분위기·직접 선택이 더 적합한가? |
| J3 | 새 곡을 기존 흐름에 맞는 위치에 넣고 싶다. | 삽입 위치 선택·추천 | 추천 위치를 이해하고 선택할 수 있는가? 후보가 여러 개면 어떻게 결정하는가? |

조사 전에는 J1~J3의 우선순위를 확정하지 않는다. 기능별 구현량보다 실제 사례의 반복성, 부담, 기존 대안, 해결 가능성을 기준으로 선정한다.

## 4. 설계 원칙과 현재 MVP의 한계

1. 같은 아티스트라도 떨어진 위치가 사용자의 의도일 수 있다. 이를 오류나 잘못된 배치로 단정하지 않는다.
2. 정렬해서 보는 상태와 저장된 감상 순서를 구분한다. 정렬 보기 종료 후 원래 순서로 돌아올 수 있어야 한다.
3. 순서를 실제로 바꾸는 경우 위치를 미리 보여주고, 사용자 실행과 되돌리기를 제공한다.
4. 기존 곡 사이의 상대적 순서는 명시적으로 선택한 변경 범위를 제외하고 보존한다.
5. 단순하고 결정적인 규칙으로 시작한다. 데이터 근거 없이 AI 추천 또는 취향 알고리즘이라고 포장하지 않는다.
6. 드래그 외에도 클릭·키보드로 사용할 수 있는 조작 경로를 설계한다.

현재 코드 기준 진단이며 사용자 테스트 결과는 아니다.

| 현재 동작 | 한계 | 이후 설계에서 확인할 항목 |
|---|---|---|
| 가장 큰 아티스트 블록을 메인으로 지정하고 나머지를 misplaced로 판정 | 의도적인 분산 배치까지 문제로 취급한다. | 중립적인 후보 표시, 사용자 지정 위치 |
| 비메인 블록을 목록 위 트레이로 분리 | 저장된 순서와 화면 표시가 달라져 기존 방식 비교를 왜곡할 수 있다. | 원래 위치 보존, 기존·개선 화면의 조건 분리 |
| 비메인 블록 카드에 첫 곡만 표시 | 복수 곡 구간에서 일부 곡이 화면상 누락될 가능성이 있다. | 여러 곡이 있는 분산 구간을 포함해 확인 |
| 아티스트순은 연속 블록을 가나다순으로 표시 | 하나의 아티스트가 여러 블록으로 남을 수 있고 감상 순서와 보기 순서가 불명확하다. | 보기 모드와 편집 적용의 명시적인 구분 |
| 신규 곡을 가장 큰 블록 뒤로 이동 | 가장 큰 구간이 사용자가 원하는 위치라는 근거가 없다. | 여러 후보, 앞뒤 맥락, 거절·직접 선택 |
| 데모 대시보드와 보조 기능을 함께 노출 | 처음 보는 사람이 핵심 과제를 파악하기 어려울 수 있다. | 짧은 안내 시나리오와 자유 체험 분리 |

위 표는 1단계의 초기 코드 진단이다. 후속 모바일 적용안에서는 자동 오류 판정·상단 트레이를 제거하고 모든 구간 선택, 보기 순서 분리, 편집 임시 상태·복원을 구현했다. 이전 구현은 기록으로 남아 있다. 사용자 필요와 정확한 현행 UI를 확인하는 과제는 계속 남아 있다.

## 5. 전체 진행 순서와 단계별 산출물

| 단계 | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 1. 문제 정의·검증 준비 | 경험·사실·가설 분리, 대상·과제 정의, 조사 도구 작성 | 이 문서와 조사 기록지 | 준비 문서 작성 완료. 실제 서비스 확인·조사는 별도 미완료로 표시 |
| 2. 현재 동작·사용자 필요 확인 | 멜론·경쟁 서비스 직접 관찰, 약 5명 탐색 인터뷰 | 버전별 동작 기록, 익명 사례, J1~J3 우선순위 결정 | 구체적인 최근 사례와 대안·반례를 기록하고 진행·축소·전환 결정 |
| 3. 핵심 경험 설계 | 선정 과제의 흐름·상태·예외 설계 | 화면 흐름, 미리보기·적용·되돌리기 규칙, 비교 시나리오 | 의도적인 분산 배치와 보기/실제 순서 차이를 설명 가능 |
| 4. 핵심 구현·완성도 개선 | 선정 기능, 모바일·키보드 조작, 결과 피드백, 초기화 구현 | 조작 가능한 데모와 필요한 로직 검증 | 곡 누락·중복·뜻하지 않은 순서 변경 없이 과제 수행 및 복원 가능 |
| 5. 사용성 비교·수정 | 동일 조건 과제 비교, 문제에 따라 수정 | 참여자별 측정 기록, 변경 전후 설계와 이유 | 실패 사례 포함 기록, 효과와 한계를 분리해 설명 가능 |
| 6. 배포·포트폴리오 구성 | 체험 링크, 짧은 시연, 사례 문서, README 정리 | 배포 데모·사례 페이지 또는 문서·저장소 소개 | 처음 보는 사람이 문제·판단·결과·한계를 이해하고 체험 가능 |

배포 방식·외부 계정 연결은 해당 단계에서 선택한다. 지금은 외부 서비스에 게시하지 않는다.

## 6. 검증 질문과 진행 판단

| 가설 | 필요한 증거 | 약해지는 경우의 대응 |
|---|---|---|
| H1. 순서를 직접 관리하며 반복적인 부담을 겪는 사용자가 있다. | 최근 편집 사례, 관리 기준, 불편 때문에 포기하거나 우회한 사례 | 사례가 드물면 대상 범위를 좁히거나 개인 사례 중심 실험으로 명시 |
| H2. 아티스트가 유용한 묶음 기준이다. | 실제 목록과 사용자 설명에서 아티스트 기준을 확인 | 분위기·앨범 등이 우세하면 사용자가 선택하는 묶음으로 전환 검토 |
| H3. 기존 방법보다 과제 수행 부담을 줄일 수 있다. | 기존 대안 관찰 후 동일 과제에서 시간·완료·오류 비교 | 기존 정렬·검색으로 충분하면 이미 해결된 기능은 제외 |
| H4. 위치 미리보기와 되돌리기가 순서 변경을 이해하는 데 도움이 된다. | 실제 삽입 위치 설명, 선택 이유, 복원 성공 | 안내나 자동 스크롤이 혼란을 만들면 수정하거나 제거 |

약 5명은 탐색을 위한 계획이며 시장 규모를 추정하는 표본이 아니다. 몇 명이 동의했다는 숫자만으로 진행을 결정하지 않는다. 구체적인 사례가 서로 다른 참여자에게서 반복되는지, 기존 방법의 한계가 있는지, 유용한 반례가 무엇인지 검토한다.

현재 멜론 앱을 직접 확인할 수 없다면 조사 대기 상태로 남긴다. 기억에 기반한 시뮬레이션을 최신 앱 재현으로 표기하지 않는다. 경쟁 서비스의 도움말에 기능이 없다고 적혀 있지 않은 것과 실제 기능 부재는 구분한다.

## 7. 결과 측정 계획

설계 확정 뒤 기존·개선 과제를 같은 데이터, 시작 순서, 목표 위치, 기기에서 비교한다. 체험 순서는 참여자별로 번갈아 배치하고 연습·안내 조건을 동일하게 한다. 기존 화면에는 개선안의 트레이·추천·강조를 넣지 않는다.

- 주 지표: 정해진 목표 위치로 이동·추가를 완료하기까지의 시간, 성공 여부, 잘못된 순서 변경·곡 누락·중복.
- 보조 지표: 조작 횟수, 탐색·스크롤 부담, 도움 요청, 삽입 위치를 설명할 수 있는지, 되돌리기 성공.
- 주관 평가: 예상한 위치에 들어갔는지, 의도하지 않은 변경이 없다고 느끼는지와 이유.

목표 위치를 지정한 과제는 조작 효율 평가에 사용한다. 추천의 적합성은 사용자가 원하는 위치를 자유롭게 선택하는 별도 과제로 확인한다.

측정 기준과 시작·종료 조건은 테스트 전에 고정한다. 중도 실패도 기록하며 성공 사례만 평균 내지 않는다. 결과는 참여자 수, 기기, 데이터 규모, 과제 조건과 함께 제시한다. 아직 측정 결과나 개선율은 없다. 구독 유지율·이탈 방지·매출 효과는 이 실험으로 입증할 수 없다.

## 8. 포트폴리오에 사용할 이야기의 골격

1. 약 10년간 이용한 서비스에서 떠난 경험을 돌아봤다.
2. 가격·콘텐츠·탐색·편의성 문제를 구분하고, 반복해서 겪은 목록 관리 과제를 선택했다.
3. 아티스트 정렬, 블록 이동, 새 곡 삽입을 별개 과제로 정의했다.
4. 다른 사용자의 실제 사례와 현재 서비스 동작을 확인했다. **미실시: 조사 후 작성.**
5. 근거를 바탕으로 기능을 선택하고, 사용자의 기존 순서를 보존하는 경험을 설계했다. **미실시: 설계 후 작성.**
6. 동일한 과제로 비교하고 실패 사례를 반영했다. **미실시: 테스트 후 작성.**
7. 측정한 변화와 남은 한계를 공개했다. **미실시: 결과 확보 후 작성.**

‘자동 정렬로 사용자 이탈 해결’, ‘업계 최초’, ‘모든 사용자의 문제’, ‘젊은 이용자 복귀’, ‘조사 결과가 증명한 시장 수요’는 현재 사용할 수 없는 표현이다.
