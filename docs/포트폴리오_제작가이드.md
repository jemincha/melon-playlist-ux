# 멜론 UX 개선 포트폴리오 제작 가이드

## 문서 명칭과 관리 목적

2026-10-11부터 `public/portfolio/index.html`을 **‘멜론 포폴(포트폴리오)’**로 지칭한다. 일회성 목업이 아니라 프로젝트와 함께 발전시키는 공식 소개 자료로 관리한다. 최종 활용 목적은 취업 지원과 향후 개인 도메인의 포트폴리오 사이트다.

프로젝트의 의미 있는 기능·설계·조사·피드백·검증 변경은 같은 작업에서 포폴에도 반영한다. 관련 원고와 캡처, 시연·근거 링크를 함께 확인하며, 구현 여부와 실제 사용자 효과를 구분한다. 상세 작업 원칙은 저장소 루트의 `AGENTS.md`에 기록한다.

## 핵심 내러티브

**발견한 음악을, 내 취향의 순서로.**

음악을 발견하는 것만큼 발견한 음악을 정리하고 다시 듣는 경험도 중요하다. 10년의 멜론 사용 경험에서 출발해, 사용자가 만든 플레이리스트의 흐름을 유지하는 곡 추가·편집 경험을 제안했다.

이 프로젝트가 보여줄 역량은 거대한 플랫폼 전략을 제안했다는 사실보다, 문화 콘텐츠의 사용 맥락을 이해하고 문제를 좁혀 동작하는 해결책까지 만든 과정이다.

## 이번 목업

- 위치: `public/portfolio/index.html`
- 개발 서버에서: `/portfolio/`
- 시뮬레이터: `/` (소개 페이지의 프로토타입 링크)
- 별도의 패키지 없이 동작하는 HTML/CSS 페이지. 설계 결정은 native details로 열고 닫는다.
- 사용한 화면: 기존 프로토타입의 실제 코치마크 캡처 2개. 첫 화면의 목록은 설계 개념 도식으로 명시했다.
- 브라우저 인쇄로 PDF 초안을 만들 수 있다. 제출 전 페이지 나눔과 링크를 확인한다.

현재는 페이지 구성과 원고를 검토하기 위한 로컬 목업이다. 공개 배포·PPT 파일 제작은 이번 산출물에 포함하지 않았다.

## 웹 구성과 PPT 전환안

웹에서는 7개 장으로 연결하고, PPT에서는 다음 12장으로 나눈다. 발표 자료는 한 장에 하나의 주장만 남기고 세부 근거는 발표자 노트나 부록에 배치한다.

| 장 | 제목 / 핵심 주장 | 화면 또는 근거 | 발표 시 연결 문장 |
|---|---|---|---|
| 1 | 발견한 음악을, 내 취향의 순서로 | 제안 도식 + 역할·진행 단계 | 추천 이후의 정리·재감상 경험에 집중했습니다. |
| 2 | 10년간 썼지만 떠났다 | 개인 경험 타임라인, 불편 후보 | 이탈의 이유 전체를 기능 하나로 해결할 수는 없었습니다. |
| 3 | 큰 경쟁에서 작은 반복 작업으로 | 가격·콘텐츠·차트·관리 문제 선택표 | 제가 직접 관찰하고 구현해 검증할 수 있는 문제를 골랐습니다. |
| 4 | 누구의 어떤 작업인가 | 수백 곡을 순서까지 관리하는 타깃 가설 | 이번 타깃은 모든 음악 이용자가 아닙니다. |
| 5 | 새 곡 하나가 정리를 다시 요구한다 | 동일 224곡에서 225번째로 추가되는 시나리오 | 추가 뒤 위치를 찾아 옮기는 작업에 부담이 있었습니다. |
| 6 | 취향의 결정권을 남긴다 | 기존 구간 선택과 전체 재정렬의 차이 | 시스템은 제안하고 사용자가 위치를 선택합니다. |
| 7 | 블록 전체와 내부 편집을 나눈다 | 실제 블록 이동·내부 곡 이동 화면 | 두 작업의 이동 범위가 다르므로 조작도 분리했습니다. |
| 8 | 실제 액션으로 차이를 체험한다 | 코치마크 화면 + 시연 링크 | 비교 화면을 읽게 하는 대신 같은 곡을 직접 담게 했습니다. |
| 9 | 실제 편집에서 막힌 동작을 고쳤다 | 키보드 정렬 대상 혼선 / 블록 내부 편집 누락: 문제 → 원인 → 수정 → 확인 | 블록과 내부 곡의 이동 범위를 분리하고 실제 목록 변경으로 확인했습니다. |
| 10 | 구현에서 지킨 규칙 | 임시 편집 상태·취소·되돌리기·순서 보존 | 화면의 약속이 실제 데이터 동작에서도 유지되도록 구현했습니다. |
| 11 | 구현 검증과 사용자 검증은 다르다 | 확인한 것 / 미확인한 것 / 다음 조사 | 현재는 동작 검증까지이며 실제 효과는 다음 검증 대상입니다. |
| 12 | 콘텐츠 소비에서 취향을 쌓는 경험으로 | 배운 점, 기여 범위, 코드·체험 링크 | 문화 서비스의 이용 맥락을 제품의 동작으로 연결하는 일을 하고 싶습니다. |

## 제작 원칙

### 사실·관찰·가설 구분

- 가격, 차트 고착화, 이용자 고령화, 브랜드 가치 하락을 검증된 시장 사실처럼 쓰지 않는다. 개인의 당시 인식과 문제 탐색 배경으로 표시한다.
- 구현한 기본 편집 모형을 최신 멜론 앱의 정확한 재현이라고 소개하지 않는다. 공식 자료에서 확인한 요소와 재구성한 상세 화면을 구분한다.
- 225번째와 217번째는 동일 예제의 삽입 위치다. 단축 시간·효율 개선율로 해석하지 않는다.
- 대화 피드백에 따른 수정은 사용자 연구 결과와 구분한다. 인터뷰 인용, 참여자 수, 만족도, 유지율은 실제로 확보한 뒤 추가한다.
- 공식 의뢰 프로젝트가 아니라 개인 개선 제안임을 표시한다.

### 보여줄 것은 기능 수보다 판단

각 기능은 ‘무엇을 만들었나’ 다음에 ‘왜 그 방식을 골랐나’를 붙인다.

- 아티스트 정렬: 저장 순서를 바꾸지 않는 보기 정렬.
- 새 곡 추가: 원하는 기존 구간을 직접 선택.
- 블록 편집: 묶음 위치와 내부 곡 순서를 별도로 조정.
- 분리된 구간: 사용자의 의도일 수 있으므로 강제로 합치지 않음.
- 편집 상태: 저장 전 취소 가능, 최근 변경 1회 되돌리기.
- 체험: 한 진입점과 단계별 코치마크로 핵심 액션 유도.

### 트러블슈팅의 층위

트러블슈팅은 실제 구현에서 발생한 문제 또는 사용자가 편집 과제를 끝내지 못하는 기능·사용성 문제를 다룬다. ‘시연할 때 기능을 찾기 어려웠다’, ‘포트폴리오 설명 없이 개선 의도를 이해하기 힘들었다’, ‘체험 경로가 중복됐다’는 발표·시연 구성의 수정이다. 이를 제품의 기술 트러블슈팅으로 내세우지 않는다.

현재 소개할 사례는 두 개다. 상세 근거는 `docs/트러블슈팅_기록.md`에 기록했다.

1. 비활성 내부 sortable 등록 때문에 블록 키보드 이동의 대상이 곡으로 잡힌 구현 문제. 초기에는 내부 등록을 제거하고, 이후 내부 편집을 추가할 때 두 이동 영역을 분리했다.
2. 묶음 편집에서 내부 곡의 순서를 바꿀 수 없던 기능 누락. 내부 조작을 추가하고 이동 범위를 블록 안으로 제한했다.

각 사례는 문제·발생 조건·원인·수정·확인한 결과로 구성한다. 로컬 검증과 일반 사용자 조사를 구분한다. 설계상 위험에 대한 예방 조치를 실제로 발생한 버그나 사용자가 겪은 사건처럼 쓰지 않는다. 코치마크는 시연 구성에, 순서 보존·취소·되돌리기는 설계 원칙에 배치한다.

### 시각 구성

- 따뜻한 회백색 배경과 진한 녹색을 사용해 시뮬레이터의 검은 UI와 구분한다. 멜론 앱 복제 화면으로 보이게 만들지 않는다.
- 큰 제목, 짧은 주장, 실제 화면 또는 도식, 근거 주석 순서로 읽히게 한다.
- 첫 화면의 개념 도식과 실제 시뮬레이터 캡처를 구분한다.
- 화면 캡처는 읽을 수 있는 크기로 배치하고 설명은 이미지 밖 텍스트로 제공한다.
- PPT 제작 시 작은 모바일 화면 여러 개를 한 장에 넣지 않는다. 추가 위치, 블록 이동, 내부 편집은 분리한다.
- 출처, 연구 한계, 검증 단계는 작은 면책 문구에만 숨기지 말고 해당 주장 가까이 둔다.

## 다음에 확보할 자료

1. 실제 현행 모바일 앱에서 곡 추가·정렬·다중 이동 동작을 확인한 기록. 플랫폼·버전·확인 날짜와 캡처를 함께 남긴다.
2. 순서를 직접 관리하는 사용자의 실제 사례. 어떤 기준으로 묶는지, 같은 아티스트가 여러 구간에 있는 이유를 듣는다.
3. 동일 과제의 기본 모형/개선안 사용성 관찰. 체험 순서를 교차하고 코치마크 없는 첫 사용도 별도 관찰한다.
4. 완료 시간·성공 여부·잘못된 이동·안내 필요 여부. 소규모 탐색 조사의 한계를 함께 적는다.
5. 관찰 후 수정한 설계. 결과가 예상과 다르면 왜 바꿨는지 기록한다.

## 제출 전에 바꿀 부분

- 본인 이름과 지원 직무는 확인 후 추가한다. 목업에는 임의의 이름·연락처를 넣지 않았다.
- 기간·실제 기여 범위는 기록과 맞춰 쓴다. 협업 여부와 도구의 도움을 실제 작업 과정에 맞게 설명한다.
- 사용자 검증을 마치면 ‘검증 전’ 표시와 미확인 항목을 업데이트한다. 해결하지 못한 부분도 남긴다.
- 로컬 체험 링크는 소개 페이지와 시뮬레이터를 함께 배포한 주소로 교체하거나 실제 제출 환경에서 확인한다.
- 30–60초 시연 영상은 신곡 추가 → 구간 선택 → 블록 이동 → 내부 편집을 보여주되, 원래 목록이 보존되는 순간을 포함한다.

기획 직무에서는 문제 선택과 설계 근거를 먼저, 프론트엔드 직무에서는 상태·이동 규칙과 검증을 먼저 강조할 수 있다. 프로젝트의 핵심 문제와 사실관계는 바꾸지 않는다.
