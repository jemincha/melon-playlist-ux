> 개발 프로젝트 6기 (Phase 2: 개발 가이드라인)
> 작성일: 2026-08-31

---

## 1. 개발 원칙

기존 프로젝트들(계산기, Todo, 영화검색, 날씨, 음악앱, 지진앱)에서 이어온 방식을 그대로 따른다.

- **단계별 확인**: 각 단계가 눈으로 확인 가능한 상태로 동작함을 확인한 뒤 다음 단계로 진행
- **전체 교체 스크립트 선호**: 구조적 변경이 있는 경우 diff 패치보다 파일 전체를 새로 작성
- **작게 시작해서 넓히기**: 아티스트 블록 인식 → 자동 삽입 → 정렬 토글 → 비교 뷰 순으로, 핵심 기능(As-Is/To-Be 재현)이 먼저 동작한 뒤 부가 기능 추가
- **막히면 원인부터 확인**: 지진 앱에서 겪은 "전역 변수 누락", "Promise.all 조용한 실패" 같은 패턴을 염두에 두고, 에러 없이 안 되는 경우 콘솔/상태값부터 점검

## 2. 프로젝트 구조

```
melon-playlist-ux/
├── public/
│   └── dummy-data.json        # 더미 플레이리스트 데이터
├── src/
│   ├── components/
│   │   ├── PlaylistView.jsx   # 전체 플레이리스트 리스트 렌더링
│   │   ├── TrackItem.jsx      # 곡 한 줄 (곡명/아티스트/앨범아트)
│   │   ├── ArtistBlock.jsx    # 같은 아티스트 곡 그룹 시각화
│   │   ├── AddTrackButton.jsx # 곡 추가 시뮬레이션 트리거
│   │   ├── SortToggle.jsx     # 기본순/아티스트순 토글 (선택 기능)
│   │   └── CompareView.jsx    # As-Is / To-Be 비교 데모 (선택 기능)
│   ├── hooks/
│   │   └── usePlaylist.js     # 플레이리스트 상태 로직 (추가/이동/정렬)
│   ├── data/
│   │   └── dummyTracks.js     # 더미 데이터 생성/로드
│   ├── utils/
│   │   └── groupByArtist.js   # 아티스트 블록 그룹핑 로직
│   ├── App.jsx
│   └── main.jsx
├── README.md
└── package.json
```

**폴더 원칙**: `components`는 화면에 보이는 것, `hooks`는 상태/로직, `utils`는 순수 함수. 이 프로젝트는 백엔드가 없으므로 `api/` 폴더는 만들지 않음 (지진 앱과 가장 다른 점).

## 3. 컴포넌트 설계 가이드

- **상태는 최상위(App 또는 커스텀 훅)에 모으고, 하위 컴포넌트는 props로만 받는다** — 지진 앱의 `currentGeoLayer` 전역 변수 문제처럼 상태가 흩어져서 생기는 버그를 방지하기 위함
- `usePlaylist` 훅 하나가 플레이리스트의 "진실의 원천(source of truth)" 역할을 함:
  - `tracks` (현재 곡 목록 상태)
  - `addTrack(newTrack)` — As-Is 동작 재현 (맨 뒤 추가)
  - `insertIntoArtistBlock(trackId, artistName)` — To-Be 동작 (블록 삽입)
  - `toggleSort(mode)` — 선택 기능
- `ArtistBlock`은 시각적 그룹 표시만 담당하고, 실제 그룹핑 계산은 `utils/groupByArtist.js`에서 순수 함수로 분리 (테스트/디버깅이 쉬워짐)

---

## 4. 상태 관리 전략

- 규모가 작으므로 **Redux 같은 외부 상태관리 라이브러리는 사용하지 않음** — `useState` + 필요 시 `useReducer` 수준으로 충분
- 드래그 앤 드롭은 `dnd-kit` 또는 `react-beautiful-dnd` 중 택1 (둘 다 가벼운 학습곡선, 구현 시작 시점에 최신 유지보수 상태 확인 후 결정 — react-beautiful-dnd는 유지보수가 뜸해진 시기가 있었으니 확인 필요)

---

## 5. 네이밍/코드 스타일 컨벤션

- 컴포넌트: PascalCase (`TrackItem.jsx`)
- 훅/유틸 함수: camelCase, 훅은 `use` 접두어
- 더미 데이터 필드명은 실제 멜론 API 유사 형태로 맞춰 향후 실 API 연동 시 전환 부담을 줄임 (예: `trackId`, `artistName`, `albumArt`, `addedAt`)
- 커밋 단위로 하나의 기능만 다루기 (한 커밋에 여러 컴포넌트 동시 신규 생성 지양)

---

## 6. 더미 데이터 설계 가이드

- 아티스트 10~15팀, 곡 50~80개 규모 (기획서 6절과 동일)
- 최소 3~4개 아티스트는 곡이 5개 이상 몰려 있어야 "블록"이 시각적으로 체감됨
- `addedAt` 필드를 넣어 최근 추가된 곡을 구분 가능하게 (As-Is 데모에서 "방금 추가된 곡이 안 어울리는 위치에 있다"를 보여주기 위함)

## 8. 진행 방식 (체크포인트)

| Phase | 확인 기준 | 완료 후 |
|---|---|---|
| 1 | 더미 데이터가 화면에 리스트로 뜨는가 | README에 진행상황 기록 |
| 2 | 같은 아티스트 곡이 시각적으로 묶여 보이는가 | 커밋 |
| 3 | "곡 추가" 클릭 시 맨 뒤에 붙는 As-Is 동작이 재현되는가 | 커밋 |
| 4 | 추가된 곡을 블록으로 옮기면(드래그 또는 버튼) 정상 삽입되는가 | 커밋 + 여기까지가 MVP 완성선 |
| 5~6 | 선택 기능, 여유 있을 때만 진행 | 커밋 |
| 7 | Vercel/GitHub Pages 배포 후 실제 링크로 동작 확인 | README 최종 정리 |

**MVP 완성선은 Phase 4까지.** 여기까지만 되어도 기획서의 성공 기준(As-Is 불편함 전달 + To-Be 개선 체감)을 충족함. Phase 5~6은 여유가 있을 때 추가하는 선택 사항으로 README에 TODO로 남겨둠.
