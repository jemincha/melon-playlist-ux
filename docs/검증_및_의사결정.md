# 의사결정과 검증 기록

기준일: 2026-10-09 · 비교 기준 커밋: bf1b2d1 (2026-09-07)

## 개선한 문제와 결정

| 문제 | 결정 | 대안과 한계 |
|---|---|---|
| 기존에 나뉜 같은 아티스트 구간도 오배치로 분류됨 | 추가 액션에서 명시한 pendingPlacement만 이동 후보로 사용 | 추가 시각·ID 접두어로 추정하지 않는다. 세션 내 상태이며 사용자 선호를 영구 저장하지 않는다. |
| 분리 구간 첫 곡만 표시됨 | 후보 구간의 모든 곡을 카드로 표시하고 기존 구간은 모두 목록에 유지 | 후보 영역은 실제 순서와 별도로 보여준다. |
| 가장 큰 구간으로만 이동 | 기본값은 유지하되 모든 기존 구간을 목적지로 선택 가능 | 구간의 첫 곡·곡 수로 구별한다. 구간 이름과 선호 학습은 제외한다. |
| 다른 아티스트에 드롭해도 이동이 호출됨 | 대상 블록과 곡의 아티스트를 모두 확인 | 정확한 문자열 매칭이므로 공동 아티스트·동명이인 처리는 제외한다. |
| 같은 아티스트의 별개 구간 간 트랙 재정렬 가능 | 동일한 연속 블록 안에서만 재정렬 | 구간 간 이동은 신곡 후보의 명시적인 이동으로 제한한다. |
| 표시 정렬 상태에서 편집하면 기본순이 바뀜 | 가나다순에서는 블록·트랙 재정렬을 비활성화 | 기본순으로 전환 후 편집하도록 안내한다. |
| 병합 뒤 여러 구간 중 다른 구간에 스크롤됨 | 아티스트명이 아닌 블록 ID로 스크롤·강조 | 블록 첫 곡이 바뀌는 재정렬 시 ID도 바뀐다. |
| 초기 데이터 앨범아트가 외부 picsum URL에 의존함 | 초기 목록과 신곡 모두 로컬 이니셜 SVG 생성기를 사용 | 실제 앨범 이미지를 구현한 것은 아니다. |
| 하이라이트 해제 타이머가 즉시 정리됨 | 강조와 스크롤 타깃을 타이머 완료 시 함께 해제 | 추가 상태 변경·언마운트 시 타이머를 정리한다. |

삽입 계산을 React 상태에서 분리한 순수 함수로 유지해 입력 불변성과 상대 순서를 검증한다. 전역 상태 라이브러리나 백엔드는 이 과제에 필요하지 않아 추가하지 않았다.

## 기술 검증 결과

- `npm ci`: 완료. 잠금파일 변경 없음.
- `npm test`: 18개 통과, 실패 0.
- `npm run build`: 성공.
- `npm run lint`: 성공.
- Chromium 153 데스크톱(1440×1000)·모바일 폭(390×844)에서 프로덕션 빌드 조작 확인: 초기 224곡 전부 표시, 신곡 추가·버튼 이동, 기존 곡 상대 순서 보존, 하이라이트 표시·해제, 가나다순 편집 제한, 이동 후보 선택·삭제 통과.
- 별도 8곡 테스트 화면에서 기존 아티스트 2구간 + 연속 신곡 2곡을 구성: 모든 곡 표시, 작은 구간 지정 이동, 남은 신곡 표시·이동 통과. 이 화면은 제품 데이터가 아닌 검증용 fixture다.
- 검증용 화면에서 데스크톱 포인터 드래그 확인: 다른 아티스트에 드롭하면 무변경, 같은 아티스트의 지정 구간에 드롭하면 해당 구간으로 이동.
- 모바일 가로 넘침 없음, 초기·신곡 이미지 정상 로드, 위 조작 중 브라우저 런타임 오류 없음.
- 스크린샷은 [모바일](assets/demo-mobile.png)·[데스크톱](assets/demo-desktop.png)에 기록했다. 캡처 환경의 한국어 글꼴을 제공했으며 제품의 글꼴·데이터는 바꾸지 않았다.
- 터치 기기의 실제 드래그, 키보드 조작, Safari는 미검증. 자동 화면 조작을 사용자 테스트로 간주하지 않는다.
- 실제 사용자 테스트: 미실시. 정리 시간·만족도 개선 수치 없음.
- 실제 멜론 최신 앱 대조: 미실시.

테스트 범위: 연속 구간 그룹화, 기존 분리 구간 보존, 여러 신곡 후보, 기존 구간에 연속된 추가곡 처리, 신규 아티스트 처리, 명시적 목적지 이동, 다른 아티스트·없는 목적지 거부, 다른 곡의 상대 순서와 입력 불변성, 오프라인 표시 계산.

## 사용자 테스트 계획

대상: 수백 곡의 플레이리스트 순서를 직접 정리하는 사용자 3~5명. 소표본 탐색으로 제한하며 전체 사용자 통계로 일반화하지 않는다.

1. 실제 정리 습관과 같은 아티스트를 여러 구간에 나누는 이유를 먼저 묻는다.
2. 기존 방식과 MVP에서 동일 규모 목록의 신곡을 지정 구간으로 옮기게 한다. 순서를 참가자별로 교차한다.
3. 구간 하나, 동일 아티스트 구간 여러 개, 신곡 여러 개의 세 조건을 확인한다.
4. 도구를 설명하기 전 이동 후보·목적지·결과를 이해하는지 관찰한다.
5. 과제 종료 후 실수와 원치 않는 이동, 실행 취소 필요성을 묻는다.

| 참가자 | 기준 환경·앱 버전 | 조건·수행 순서 | 기존 시간/조작 수 | MVP 시간/조작 수 | 성공·오류·도움 요청 | 의도한 구간/선택 이유 |
|---|---|---|---|---|---|---|
| 미실시 | — | — | — | — | — | — |

시작: 새 곡이 추가된 상태에서 과제를 제시한 시점. 종료: 지정 구간에 들어간 것을 참가자가 확인한 시점. 탭·클릭·드래그·스크롤 제스처를 각각 기록한다. 실패·도움 요청을 제외하고 평균을 내지 않는다. 관찰 결과는 개인별 원자료와 중앙값을 함께 보고한다.

실제 앱 대신 재현 화면으로 비교하면 그 사실과 동작 차이를 기록한다. 가장 큰 구간 선택이 자주 틀리면 기본 목적지 정책을 수정하고, 실수가 반복되면 실행 취소를 우선 검토한다.
