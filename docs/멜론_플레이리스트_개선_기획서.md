# 멜론 플레이리스트 편집 UX 개선 프로토타입 기획서

> 개발 프로젝트 6기 (Phase 1: 기획) — 기존 플랫폼 개선 프로토타입 트랙
> 작성일: 2026-08-31

---

## 1. 프로젝트 개요

**대상 서비스**: 멜론 (10년 실사용 경험 기반)
**프로젝트 형태**: 서비스 기획 문서 + React 기반 클릭 가능 프로토타입 (풀스택 아님, 프론트 단독 구현)
**핵심 한 줄**: 플레이리스트에 곡을 추가할 때, 같은 아티스트의 기존 곡들과 자동으로 묶이지 않고 흩어지는 문제를 해결한다.

---

## 2. 문제 정의

### 2.1 핵심 문제
헤비 플레이리스트 유저(수백 곡을 카테고리별로 정리해 관리하는 사용자)가 겪는 문제:

1. 특정 아티스트의 곡 5~10개를 이미 플레이리스트 안에 순서대로 정리해둔 상태에서, 해당 아티스트의 **신곡이 나와 플레이리스트에 추가**하면 항상 맨 앞이나 맨 뒤에 붙는다.
2. 사용자는 그 신곡을 **같은 아티스트 곡들이 모여 있는 위치**로 옮기고 싶지만, 곡이 많아질수록 하나씩 수동으로 드래그해 옮기는 게 부담스러워진다.
3. 결과적으로 "듣는 흐름을 유지한 채 취향껏 정리된 플레이리스트"를 유지하는 비용이 계속 커진다.

### 2.2 왜 이 문제를 선택했는가
- **개발 초급자가 2주 내 구현 가능한 범위** — 백엔드/DB 연동 없이 프론트 상태값(더미 데이터)만으로 시연 가능
- **문제-해결 스토리가 명확** — "무엇이 불편한지 → 왜 불편한지 → 어떻게 풀었는지"를 한 화면 흐름으로 보여줄 수 있음
- 가격 정책, 티켓팅 제휴, 팟캐스트 콘텐츠 경쟁력, 브랜드 전략 등 다른 후보 문제들은 사업/제휴 영역이라 프로토타입으로 증명하기 어려워 제외함 (별도 배경 설명으로만 기획서에 남김)

## 3. 문제 검증

### 3.1 개인 경험 근거
10년간 멜론을 사용하며 국내 밴드/인디 음악 위주로 수백 곡을 장르·무드별 플레이리스트로 정리해온 사용 패턴에서 반복적으로 겪은 문제.

### 3.2 경쟁사 비교로 본 문제의 보편성
가장 정교한 정렬 기능을 갖춘 스포티파이를 기준으로 확인한 결과:

- 스포티파이는 플레이리스트 전체를 <cite index="20-1">이름, 아티스트, 앨범 등 기준으로 맞춤형 순서로 정렬하는 기능을 제공</cite>하지만, 이는 **플레이리스트 전체를 한 번에 재정렬**하는 방식이지, 기존에 사용자가 커스텀 순서로 배치해둔 흐름을 유지하면서 "새로 추가된 곡만 해당 아티스트 블록으로 자동 삽입"하는 기능은 아니다.
- 실제로 이 문제를 별도로 해결해주는 서드파티 툴(Skiley 등)이 존재한다는 점 자체가, <cite index="21-1">아티스트·장르 등 기준으로 플레이리스트를 정렬하거나 중복곡을 정리하는 수요가 네이티브 앱만으로는 충분히 해소되지 않고 있음</cite>을 보여줌.
- 즉 **멜론만의 문제가 아니라 업계 전반의 미해결 영역**이며, 스포티파이보다 정렬 기능이 단순한 멜론에서는 체감 불편도가 더 큼.

### 3.3 검증의 한계
현재 멜론을 해지한 상태라 실제 최신 UI/정렬 옵션과는 차이가 있을 수 있음. 구현 전 최신 앱 UI 캡처 또는 리뷰 재확인 권장 (Phase 1 후속 작업으로 표시).

## 4. 기능 명세 (MVP)

| 기능 | 설명 | 우선순위 |
|---|---|---|
| 플레이리스트 뷰 | 더미 데이터 기반 곡 목록 표시 (곡명/아티스트/앨범아트) | 필수 |
| 아티스트 블록 인식 | 같은 아티스트의 곡들을 시각적으로 그룹화 표시 | 필수 |
| 곡 추가 시뮬레이션 | "새 곡 추가" 액션 → 기본은 맨 뒤에 붙는 As-Is 동작 재현 | 필수 |
| 블록 단위 이동 | 새로 추가된 곡을 같은 아티스트 블록으로 드래그 시 자동 정렬/삽입 | 필수 (To-Be 핵심) |
| 정렬 기준 전환 | 기본순 / 아티스트 가나다순 토글 | 선택 (여유 있으면) |
| 개선 전/후 비교 뷰 | As-Is / To-Be를 나란히 보여주는 데모 모드 | 선택 (포트폴리오 임팩트용) |

**스코프 제외**: 실제 음원 재생, 로그인/DB 연동, 서버 저장 — 모두 프론트 상태값으로만 시연.

## 5. As-Is / To-Be 플로우

**As-Is**
1. 사용자가 플레이리스트에서 "곡 추가" 클릭
2. 추가된 곡이 리스트 맨 끝(또는 맨 앞)에 위치
3. 사용자가 원하는 위치까지 수동으로 드래그 (곡이 많을수록 스크롤+드래그 반복)

**To-Be**
1. 사용자가 플레이리스트에서 "곡 추가" 클릭
2. 시스템이 추가된 곡의 아티스트를 인식
3. 플레이리스트 내 동일 아티스트 블록이 있으면 해당 위치로 자동 삽입 제안 (또는 원클릭 이동)
4. 없으면 기존 As-Is 동작(맨 끝 추가) 유지

## 6. 프로토타입 구현 범위

- **기술 스택**: React (상태관리는 useState/useReducer 수준으로 충분), 드래그 앤 드롭은 가벼운 라이브러리 활용 검토
- **데이터**: 더미 JSON (아티스트 10~15팀, 곡 50~80개 규모로 실제 플레이리스트처럼 보이게 구성)
- **백엔드**: 없음. 모든 상태는 세션 내 프론트 메모리에서만 유지
- **배포**: 완성 후 정적 호스팅(Vercel/GitHub Pages)으로 실제 링크 제공 — 포트폴리오 신뢰도 강화

---

## 7. 성공 기준 (포트폴리오 서술 기준)

- [ ] As-Is의 불편함이 3초 안에 시연으로 전달되는가
- [ ] To-Be 개선이 클릭 1~2번으로 체감되는가
- [ ] "왜 이 문제를 골랐는가"에 대한 근거(개인 경험 + 경쟁사 비교)가 기획서에 명확히 남아있는가
- [ ] 실제 배포 링크로 채용 담당자가 직접 조작해볼 수 있는가

---

## 8. 남은 배경 이슈 (구현 대상 아님, 기획서 맥락용으로만 보존)

- 가격/멤버십 경쟁력 (유튜브 프리미엄 대비)
- 유튜브 팟캐스트 생태계 종속 한계
- 차트 고착화·이용자 고령화 (참고: 멜론은 이미 '시대별 차트', 트로트 전용 DJ 플레이리스트 등 세대 세분화를 부분적으로 시도 중 — 향후 프로젝트에서 "진짜 개인화 차트" 방향으로 재정의 가능)
- 브랜드 재포지셔닝 전략 (편의성 중심 vs 중장년 타겟)
